# Library Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a Library section (files, links, text snippets) and let the preview assistant resolve "my CV" to a Library item and show it on the approval card.

**Architecture:** Same pattern as every other section: a client store in `lib/data/library.ts` seeded from `lib/mock/library.ts`, a `/library` route rendering `components/library/*`, and a new assistant scenario that calls the store's resolver. Pure logic (resolution, validation, store mutations) is unit-tested with Vitest; UI is verified by typecheck, lint, build and Playwright screenshots.

**Tech Stack:** Next.js 16 (App Router, `cacheComponents`), React 19, TypeScript, Tailwind v4, Radix, cmdk, lucide-react. Adds `vitest` (dev).

**Spec:** `docs/superpowers/specs/2026-11-25-library-design.md`

## Global Constraints

- Preview only: no network, no persistence across reloads; uploads live in memory as object URLs, revoked on delete/replace.
- Kinds are exactly `"file" | "link" | "text"`; sharing is exactly `"ask" | "never"`.
- Files up to 10 MB (`10 * 1024 * 1024` bytes).
- Every share goes through approval; a `"never"` item must never appear on an approval card.
- Anything shared in the preview is marked Simulated; nothing claims verified delivery from the Library flow except the existing scenario's simulated "Gmail confirmed delivery" step.
- Sample headshot uses a neutral placeholder, never a photo of a person.
- Follow existing tokens/components (`components/ui/*`, `Page`/`PageHeader`/`SplitView`, `cn`); no new UI dependencies.
- Sample data generated on the client via `createStore` (never at module load on the server).

## Review Focus

1. **Alias collisions:** two items sharing a name/alias ("CV" on both CV and an old CV) → resolver returns `candidates`, LANA asks; the add/edit dialog warns when an alias is already used. (Task 1 test, Task 4 test)
2. **Request with no recipient** ("send my CV") → LANA asks who to send it to instead of drafting to an empty address. (Task 6 test)
3. **Link without protocol** ("emmanuelola.dev") → normalised to `https://emmanuelola.dev`; garbage ("not a url") rejected. (Task 4 test)
4. **Item deleted while its approval is pending** → the approval can't be approved; card says the item is no longer in the Library. (Task 6 test)
5. **Non-previewable uploads** (`.docx`, `.zip`) → type tile, no broken `<img>`/`<iframe>`. (Task 5 step)

Behaviour of `sendFromLibrary` (steps exactly: "Find “my <query>” in your Library", "Draft the email", "Wait for your approval", "Send with Gmail", "Confirm delivery"):
- `none` → step 1 fails "Not in your Library"; reply offers `[Add it to your Library](/library)`; action `failed`.
- `blocked` → step 1 fails "Set to never share"; reply: "Your passport scan is set to never share, so I won't send it. You can change that in the Library."; nothing else runs.
- `candidates` → step 1 detail "2 matches"; action `cancelled`; reply lists the matches and asks which one.
- No recipient → reply asks "Who should I send it to?" before any action is created.
- `match` → approval fields To (editable), Subject (editable, "My CV" style: `"${item.name}"`), Message (editable; for `text` items the snippet is included in the body); attachments: the item. On approve: steps 4–5 run, `recordShare(item.id, { at: now, to, via: "gmail", actionId })`, `addActivityRecord` with `simulated: true`, `finish({ verified: true, summary: "Delivered to …" })` — consistent with the existing email scenario.
